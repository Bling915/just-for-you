# 小事成双对：双人体验与共同回忆设计规格

## 目标

在现有“小事成双对”MVP 上完成两个阶段的产品能力：先完善真实情侣的邀请、资料、状态陪伴、记录编辑、图片体验与通知基础，再增加纪念日、共同待办、愿望清单、日历回忆、地图回忆和月度报告。

最终用户应能从分享邀请进入情侣关系，与伴侣持续交换状态和互动，记录可补记、编辑且包含位置坐标，并在多个回忆视图中回看共同生活。单人测试模式继续可用，且与真实情侣流程使用相同业务接口。

## 范围与约束

- 后端保持单个 Go 服务、单个 MySQL 数据库，不拆微服务。
- 严格沿用全局 DDD 分层：`domain`、`application`、`infrastructure`、`interfaces`。
- 新能力按业务领域拆包，不把所有逻辑塞入 `moment` 或 `relationship`。
- 小程序保持原生微信小程序技术栈，不引入新的大型 UI 框架。
- 底部导航继续保留“首页、时光、我的”三个入口。
- 现有用户、关系、记录和照片数据必须保持兼容。
- 所有写操作仅允许当前关系中的成员执行；编辑和删除记录仅允许作者执行。
- 时间、字符数和分页规则由后端最终裁决，前端只做提前校验。

不在本次范围内：即时聊天、语音或视频通话、付费会员、公开社区、AI 生成文案、多关系并存、后台运营系统。

## 架构决策

采用 DDD 模块化单体。部署仍是一个二进制，但业务边界独立：

```text
internal/domain
  companionship
  moment
  together

internal/application
  companionship
  moment
  together

internal/infrastructure/persistence/mysql
  companionship
  moment
  together

internal/interfaces/http
  companionship
  moment
  together
```

`relationship` 继续负责建立和解除情侣关系；`companionship` 负责状态和轻互动；`moment` 负责日常记录和回忆查询；`together` 负责纪念日、待办与愿望。模块间只能通过 application 端口或只读标识交互，不能跨包直接调用基础设施实现。

## 第一阶段设计

### 邀请分享与伴侣资料

邀请页支持 `onShareAppMessage`，分享路径携带邀请码。被邀请者打开小程序后，邀请码暂存并在登录完成后自动带入绑定页。邀请码仍由服务端校验，客户端不得自行判断有效性。

情侣关系查询返回双方的公开资料：用户 ID、昵称、头像、绑定时间、是否单人测试关系。首页展示伴侣资料和相伴天数。测试关系使用清晰标识，避免用户误以为已经绑定真实伴侣。

### 状态陪伴与轻互动

`companionship` 领域包含两种实体：

- `Presence`：当前状态、可选自定义文字、可选结束时间、更新时间。
- `Nudge`：`miss_you`、`hug`、`cheer_up` 三种轻互动，记录发送者、接收者和发送时间。

预设状态包括 `in_class`、`miss_you`、`tired`，也允许最多 20 个可见字符的自定义状态。结束时间必须晚于当前时间，过期状态在读取时显示为“此刻安静地陪伴着”，历史记录保留用于月报统计。

轻互动使用独立写接口，接收者必须是当前关系中的另一方。服务端对同一发送者施加短时间频率限制，避免连续点击产生大量记录或通知。

首页读取接口整合伴侣资料、对方有效状态、最近互动和最近记录，减少首屏请求数量。

### 记录编辑与补记

`moment` 增加更新行为。作者可修改文字、状态、地点、照片顺序和记录发生时间；不可修改作者或所属关系。补记时间不得晚于当前时间，且不得早于合理产品下限 2000-01-01。

记录区分：

- `occurred_at`：事情实际发生时间，用于时间线、日历、地图与月报。
- `created_at`：记录创建时间，用于审计和并发判断。
- `updated_at`：最后编辑时间。

旧数据迁移时使用 `created_at` 填充 `occurred_at` 和 `updated_at`。更新接口接收当前 `updated_at` 作为版本条件；若记录已被其他客户端修改，返回冲突错误，前端提示重新加载。

位置扩展为地点名称、纬度和经度。纯文字位置继续兼容；地图只展示同时拥有合法经纬度的记录。

### 图片上传体验

选择图片后在客户端压缩，默认质量以清晰可读和移动网络上传速度平衡；压缩失败时允许退回原图，但仍受后端大小限制。上传队列保持最多 9 张、并发数 2。

每张图片呈现 `等待授权、压缩中、上传中、成功、失败` 状态及 0–100% 进度。`wx.request` 的上传任务监听进度；失败项显示可理解原因并允许单独重试。编辑记录时，已上传图片与新图片统一排序，只有新图片需要申请上传授权。

### 微信订阅消息

通知通过 application 端口抽象，基础设施实现调用微信订阅消息 API。通知场景包括新记录、状态更新和轻互动。

用户必须先在前端主动调用订阅授权；服务端只向已授权且开启对应场景的用户发送。通知发送失败不得导致主要业务写操作失败，失败会被记录以便排查。

模板 ID 通过环境变量配置。在模板未申请、未配置或用户拒绝授权时，设置页明确显示“暂未开启”，其余功能正常工作。本次交付完成接口、配置、授权入口、偏好存储和发送实现，但正式送达依赖微信公众平台批准的模板 ID。

## 第二阶段设计

### 纪念日

`together` 领域的 `Anniversary` 包含标题、日期、是否按年重复、创建者和创建时间。绑定日作为系统纪念日自动展示，不允许删除；用户可新增、编辑、删除自定义纪念日。

首页展示距离最近的未来纪念日及剩余天数。涉及 2 月 29 日的年度纪念日在非闰年按 2 月 28 日展示。

### 共同待办

`Todo` 包含标题、可选截止日期、创建者、完成者、完成时间和状态。双方均可创建、完成和重新打开；只有创建者可删除。列表默认将未完成项按截止日期排序，已完成项折叠显示。

### 想一起做的事

`Wish` 包含标题、可选说明、创建者、状态、完成时间和可选关联记录 ID。双方均可新增和标记完成；完成时可以关联一条共同记录，将计划与真实回忆连接起来。

### 日历回忆

日历按自然月查询，返回每天的记录数量和最多三张封面图。点击某天进入当日记录列表。查询以 `occurred_at` 和用户本地时区 `Asia/Shanghai` 分组，避免 UTC 跨日造成错位。

### 地图回忆

地图查询返回当前关系中具有坐标的记录点。相近坐标在前端聚合显示，点击标记展示地点名称、日期、封面和记录数量。地图仅上传用户主动选择的位置，不在后台持续获取位置。

### 每月回忆报告

报告按自然月确定性聚合，不调用 AI：

- 双方和各自发布数量
- 照片总数
- 最常使用的状态
- 有坐标或地点名称的去过地点
- 完成的待办和愿望
- 当月纪念日
- 精选封面记录

报告数据按需计算；没有数据时返回温暖的空状态，不伪造统计。前端将报告渲染为可分享的纵向卡片，分享只包含摘要入口，不暴露私人正文或照片给未授权用户。

## 小程序信息架构

底部导航保持不变：

- 首页：伴侣资料、有效状态、快捷互动、最近记录、临近纪念日。
- 时光：时间线，并提供日历、地图和月报入口。
- 我的：个人与关系资料，并提供纪念日、共同待办、愿望和通知设置入口。

新增页面：

```text
pages/status-editor
pages/moment-edit
pages/calendar
pages/day-moments
pages/memory-map
pages/anniversaries
pages/todos
pages/wishes
pages/monthly-report
pages/notification-settings
```

页面继续使用浅色、薰衣草、日常治愈的视觉体系。动效以轻量进入、状态反馈和完成反馈为主，不影响低性能设备上的核心操作。

## 数据持久化

新增增量迁移，至少包含：

- `presences`
- `nudges`
- `notification_preferences`
- `notification_deliveries`
- `anniversaries`
- `todos`
- `wishes`

扩展 `moments`：`occurred_at`、`updated_at`、`latitude`、`longitude`。所有情侣数据表包含 `relationship_id` 并建立关系与时间索引。软删除策略仅用于记录；纪念日、待办和愿望采用显式状态或硬删除，并通过权限检查保护。

迁移必须可重复验证，提供向下迁移；部署顺序是先执行兼容迁移，再部署同时兼容旧、新字段的服务。

## 接口原则

接口沿用 `/v1`，主要新增或扩展：

```text
GET    /v1/home
PUT    /v1/presence
POST   /v1/nudges
PATCH  /v1/moments/:id
GET    /v1/moments/calendar
GET    /v1/moments/map
GET    /v1/reports/monthly
GET    /v1/anniversaries
POST   /v1/anniversaries
PATCH  /v1/anniversaries/:id
DELETE /v1/anniversaries/:id
GET    /v1/todos
POST   /v1/todos
PATCH  /v1/todos/:id
DELETE /v1/todos/:id
GET    /v1/wishes
POST   /v1/wishes
PATCH  /v1/wishes/:id
DELETE /v1/wishes/:id
GET    /v1/notification-preferences
PUT    /v1/notification-preferences
```

错误继续使用稳定业务错误码。任何跨情侣访问都统一表现为资源不存在或无权操作，不泄露其他情侣的数据存在性。

## 错误处理与安全

- 所有请求继续要求有效访问令牌。
- 图片上传签名使用服务端凭证生成，密钥不得进入小程序包或 Git。
- 上传、互动和通知接口增加频率限制。
- 经纬度校验范围为纬度 `[-90, 90]`、经度 `[-180, 180]`。
- 微信通知调用设置超时，失败异步记录，不回滚用户已经完成的操作。
- 客户端保留草稿；编辑冲突、网络错误和部分图片失败均提供明确恢复入口。
- 解除关系后，双方不能继续读取或修改该关系下的数据。

## 测试与验收

每项行为遵循测试先行：

- domain：实体不变量、权限、日期边界、状态流转。
- application：关系成员校验、仓储交互、通知失败不影响主流程。
- infrastructure：MySQL 查询和事务、微信通知适配器、迁移。
- HTTP：参数校验、业务错误映射和响应 DTO。
- 小程序：服务层、状态仓库、日期分组、上传进度与页面关键状态。
- 手工验收：两个真实微信账号以及单人测试关系各走一遍完整流程。

最终验收路径：

```text
分享邀请 → 登录绑定 → 查看伴侣资料 → 更新状态/发送互动
→ 发布压缩图片记录 → 编辑与补记 → 时间线即时刷新
→ 新增纪念日/待办/愿望 → 日历和地图回看 → 查看月报
→ 通知配置缺失时正常降级
```

## 交付顺序

1. 修复时间线刷新，完成邀请分享、伴侣资料、状态与轻互动。
2. 完成记录编辑、补记、位置坐标、图片压缩和上传进度。
3. 完成纪念日、共同待办和愿望清单。
4. 完成日历、地图、月报和订阅消息接入层。
5. 运行完整测试、微信开发者工具验收、部署后端，并整理需要用户在微信公众平台配置的项目。
